# 个人记账 App 蓝白极简主题改造规范（AI 可执行）

> **用途**：把本文件交给 Cursor、Claude Code、Codex 或其他 AI 编程助手，要求其在**已有项目**中进行 UI/UX 改造。
>
> **目标**：参考 Weple Money Redesign 的**简洁、清晰、低装饰**的设计思路，建立统一的蓝白色记账 App 视觉体系。**仅参考设计语言，不复制受版权保护的具体页面、图标或素材。**
>
> **重要原则**：这是**现有项目的渐进式 UI 改造**，不是从零重建项目。除非确有必要，不改变业务逻辑、接口、状态管理、路由、数据结构和用户使用流程。

---

## 0. 给 AI 编程助手的执行指令（必须首先阅读）

你是一名具备移动端设计能力的资深前端 / Flutter 工程师。请先阅读当前仓库，识别技术栈、页面结构、样式体系及现有设计变量，然后严格按照此文档对**已有记账 App** 做蓝白极简主题升级。

### 工作规则

1. **先理解项目，再修改代码**：先定位主题配置、公共组件、导航、账单列表、记账输入、统计图表等真实文件；不要凭空假设目录名称。
2. **保持原有功能**：不得破坏登录、账单新增/编辑/删除、分类、预算、筛选、统计、同步、国际化、权限等已有功能。
3. **优先改公共主题**：优先通过主题 Token、公共组件与局部样式改造解决问题，避免逐页复制大量颜色、间距与按钮样式。
4. **保留现有技术架构**：不要未经请求迁移框架、替换路由/状态管理、变更接口协议、重构数据库或引入大型 UI 库。
5. **改已有页面，而非生成演示页面**：依据项目真实页面做适配；若某个示例页面在项目中不存在，不要擅自增加路由或功能。
6. **有取舍地改造**：未指定的功能、交互及组件沿用现状；如有不明确的视觉选择，以“可读性优先、少装饰、低视觉噪音”为准。
7. **不要中途停在方案阶段**：完成代码修改，并执行项目现有可运行的格式化、静态检查、测试/构建；无法执行的命令说明原因。
8. **提交可审查的结果**：最终列出修改文件、核心改动、验证结果和保留问题。不要声称未运行的测试已通过。

### 改造边界

**允许**：配色、排版、间距、圆角、边框、阴影、图标视觉、已有页面布局的轻量整理、空/加载/错误状态视觉、图表配色、导航选中态。

**默认禁止**：业务逻辑重写、API 字段变动、删除已有功能、修改交易金额计算规则、变更货币精度、修改数据存储格式、大规模目录重组、增加无需求的新模块。

## 1. 产品与视觉定位

### 产品定位

- 类型：个人记账 App / 日常收支管理。
- 主要任务：快速记一笔、查看账单、了解本月收支、查看分类统计、管理预算。
- 情绪关键词：**极简、清爽、可信、克制、轻金融、易读**。
- 视觉参考：Weple Money Redesign 的信息组织方式（收支概览、月份选择、账单列表、清晰的金额层级）。

### 视觉方向

- 以**白色 + 浅灰白**为页面基础，大面积留白。
- 以**蓝色**作为品牌与交互强调色，不要让所有卡片都变蓝。
- 尽量采用**扁平化设计**和弱分隔线，避免厚重的投影、玻璃拟态、炫光、复杂渐变。
- 财务数据优先于装饰。金额、日期、分类、账户信息必须一眼可读。
- 收入/支出的语义色用于财务结果，**不要用主蓝色替代全部财务语义色**。
- 不强行添加动画。已有动画可以保留，但时长和运动应克制。

## 2. 全局主题颜色（设计 Token）

**请把以下颜色集中维护在项目既有主题体系中。禁止在各业务组件中反复硬编码同一色值。**

### 2.1 品牌与交互色

| Token | 色值 | 使用场景 |
|---|---|---|
| `primary` | `#2F80ED` | 主要操作按钮、Tab 选中、链接、关键图表元素 |
| `primaryHover` | `#1F6FE5` | Web hover、按下态（若平台支持） |
| `primaryLight` | `#EAF3FF` | 选中背景、图标浅底、轻提示 |
| `primarySoft` | `#F0F6FF` | 次级浅蓝区块、非重点标签 |
| `onPrimary` | `#FFFFFF` | 主蓝背景上的文字与图标 |

### 2.2 背景与线条

| Token | 色值 | 使用场景 |
|---|---|---|
| `background` | `#F7FAFC` | App 页面背景 |
| `surface` | `#FFFFFF` | 卡片、列表、输入区域 |
| `surfaceSecondary` | `#F0F6FF` | 浅蓝辅助容器（少量使用） |
| `border` | `#E6ECF2` | 分割线、输入框、轻边框 |
| `divider` | `#E6ECF2` | 列表分隔 |

### 2.3 文字

| Token | 色值 | 使用场景 |
|---|---|---|
| `textPrimary` | `#1B2633` | 页面标题、金额、重要信息 |
| `textSecondary` | `#5B6B7A` | 分类说明、日期、次要文案 |
| `textPlaceholder` | `#9AA8B6` | 输入提示、弱信息 |
| `textDisabled` | `#BCC7D3` | 禁用内容（需搭配其他禁用提示） |
| `textOnPrimary` | `#FFFFFF` | 主色按钮文案 |

### 2.4 财务语义色

| Token | 色值 | 使用场景 |
|---|---|---|
| `income` | `#27AE60` | 正向收支、收入标识 |
| `incomeLight` | `#EAF8F0` | 收入信息浅底 |
| `expense` | `#EB5757` | 支出、负向金额标识 |
| `expenseLight` | `#FDEEEE` | 支出信息浅底 |
| `warning` | `#F2994A` | 预算临界、提醒 |
| `warningLight` | `#FFF4E8` | 预算提示背景 |

> **无障碍要求**：色彩仅作为辅助区分，收入/支出同时展示 `+` / `−` 符号或明确文字；小字号正文应检查对比度。若 `income`、`expense` 或占位文字在某背景上对比度不足，可在**不改变品牌主色定位**的前提下，为正文另设深色文字变体；禁止为了追求统一而牺牲可读性。

### 2.5 色彩比例

- 约 **70%**：白色、灰白背景。
- 约 **20%**：蓝色系品牌强调及浅蓝区域。
- 约 **10%**：收入、支出、预算警告等语义色。

比例仅作为视觉倾向，**不是必须逐像素遵循的计算指标**。

### 2.6 颜色使用禁忌

- 不要使用大面积高饱和蓝色背景铺满页面。
- 不要在一个页面同时使用多种互相竞争的主色。
- 不要每张卡片都套渐变色。
- 不要在金额、按钮、状态上随意混用语义色。
- 不要使用粗重阴影、发光边框和高频动效。

## 3. 字体、间距、圆角、图标

### 3.1 字体与字号

优先沿用项目当前适合中文的系统字体 / 字体方案，避免引入不必要的字体包。

| 元素 | 推荐字号 | 字重 |
|---|---:|---|
| 页面标题 | 22–24 | 600–700 |
| 核心余额/金额 | 28–32 | 600–700 |
| 模块标题 | 16–18 | 600 |
| 列表标题/分类名 | 15–16 | 500–600 |
| 正文 | 14–16 | 400–500 |
| 时间/辅助文字 | 12–13 | 400 |
| 辅助标签 | 12–14 | 500 |

- 金额要突出，货币符号可以比数字略小。
- 数字列建议使用**等宽数字**（tabular numbers），减少金额跳动。
- 不要把全部文字做成浅灰色，需保留明显的信息层级。

### 3.2 间距系统（建议 4pt 基准）

`4 / 8 / 12 / 16 / 20 / 24 / 32`

- 页面水平内边距：**16–20**。
- 模块间距：**20–24**。
- 卡片内部边距：**16–20**。
- 列表行间距：根据可读性选择 **12–16**，优先保留原有点击区域大小。
- 图标与文字间距：**8–12**。

### 3.3 圆角与阴影

| 元素 | 圆角 |
|---|---:|
| 主卡片 | 16–20 |
| 普通卡片 | 12–16 |
| 输入框 | 12 |
| 按钮 | 12 |
| 小标签 | 8–12 |

- 卡片默认白底，优先使用轻边框或自然留白。
- 需要阴影时仅使用极浅阴影，不制作明显悬浮效果。

### 3.4 图标

- 优先使用项目现有图标体系，保持**线性、笔画统一、尺寸统一**。
- 账单类别图标可放在浅蓝/浅灰圆形背景上。
- 保持视觉统一，不要混杂多种不同风格的图标素材。

## 4. 已有页面改造规范

> **只改造项目中已经存在的页面及功能**。下面按常见记账 App 场景说明；若名称不同，以仓库中的真实页面为准。

### 4.1 首页 / 收支总览

**目标**：用户打开 App 后，快速看到本月支出、收入、结余及最近账单。

建议结构（按已有信息适配，不强行重排业务流程）：

1. 顶部：页面标题、当前月份切换、已有的设置/搜索等入口。
2. 重点区域：本月总支出、收入、结余或总资产（以项目真实已有指标为准）。
3. 次级区域：收入与支出的简洁对比卡片或信息行。
4. 下方：按日期分组的最近账单，清晰展示类别、备注、时间、金额。
5. 底部：保留原有导航栏结构与入口。

样式约束：

- 首页以 `background` 作为背景，主要数据面板使用 `surface`。
- 大金额使用 `textPrimary`；主蓝只用于月份选中态、按钮、图表重点等。
- 收支分类可以用轻量语义色，但避免大面积红绿块。
- 余额卡片**优先白底**；不要默认使用浓蓝渐变大卡。
- 页面要“轻”：减少重复标题、重复边框与不必要装饰。

### 4.2 账单明细页

- 白底或浅灰白背景，分组以“日期”为主要层级。
- 列表左侧：分类图标；中间：分类名称 + 备注/账户；右侧：金额。
- 支出显示 `−`，收入显示 `+`，且语义统一。
- 金额右对齐，字体权重大于次要信息。
- 筛选、搜索、日期切换沿用已有交互，不更改查询逻辑。
- 选中筛选项可使用 `primaryLight` 背景与 `primary` 文字/图标。
- 保持列表可滚动、可点击区域与手势操作行为。

### 4.3 新增 / 编辑记账页

**这是高频页面，重点优化易用性。**

- 金额输入是页面视觉焦点，建议字号 **28–32**。
- 收入 / 支出切换使用简洁分段控件，选中用主蓝或浅蓝底。
- 分类选择使用统一线性图标和清晰标签。
- 日期、账户、备注、标签等保留现有字段和校验。
- 主操作按钮使用 `primary` + 白色文字，标题如“保存”“完成”遵循原项目文案。
- 输入框使用 `surface` + `border`，聚焦态可显示淡蓝边框。
- **绝对不要修改金额精度、四舍五入、负数规则、币种换算和表单验证。**

### 4.4 统计 / 报表页

- 以可读性和数据准确性优先，减少花哨的图表装饰。
- 推荐简单**柱状图、折线图、环形图**，不使用 3D 或复杂高光效果。
- 主数据使用 `primary`，次数据可使用 `#56A3FF`、`#A9D1FF`、`#D9E8F8`。
- **若图表各扇区表示不同消费类别，必须保证类别可区分，不要全部使用近似蓝色**；可使用项目原有分类色、图例及明确标签。
- 坐标线 `border`，标签 `textSecondary`，关键数值 `textPrimary`。
- 时间筛选（周、月、年）选中态使用 `primaryLight` + `primary`。
- 不改变统计口径、数据源、排序规则及计算逻辑。

### 4.5 预算 / 资产 / 账户管理（如果项目已存在）

- 进度条以蓝色为主；接近预算上限时展示 `warning`；超出预算使用已有警告语义。
- 一张卡片只突出一项重点数据，其他内容尽量简洁。
- 账户列表维持统一图标、名称、余额布局。
- 不自动添加新的储蓄目标、银行卡连接或金融功能。

### 4.6 我的 / 设置

- 白色列表分组 + 细分隔线，避免大面积配色块。
- 原有账户、备份、同步、主题、语言、安全等功能保持不变。
- 危险操作保持明确的警告样式，不要改为普通主蓝按钮。

## 5. 通用组件规范

### 顶部导航栏
- 与页面背景自然融合；标题使用 `textPrimary`。
- 返回、筛选、设置图标使用 `textPrimary` 或 `textSecondary`。
- 减少粗边框，不使用明显渐变。

### 底部导航栏
- 保留原有导航项数量、顺序、路由和点击行为。
- 选中图标 / 文字：`primary`。
- 未选中图标 / 文字：`textSecondary`。
- 背景：`surface`；顶部按需加一条极浅分割线。

### 按钮
- 主要按钮：`primary` 背景 + `onPrimary` 文字，圆角 12。
- 次要按钮：`primaryLight` 背景 + `primary` 文字。
- 轻按钮：纯文字或极淡边框，避免无意义的实体色块。
- 禁用与加载状态保持明显区分，不能只依赖颜色。

### 卡片、列表与表单
- 卡片优先 `surface`，不要在整页叠加多重阴影。
- 列表分隔线使用 `divider`，位置可依据原页面结构调整。
- 输入框默认边框 `border`；激活态使用主蓝轻量高亮。
- 弹窗和底部抽屉沿用原有组件与手势行为，仅统一视觉。

### 空状态、加载、错误
- 使用简短文案与轻量图标，不加入大幅插画。
- 加载状态保留已有 Skeleton / Spinner 逻辑，颜色统一主蓝与灰白。
- 错误、成功、警告必须通过文字/图标传递语义，不能只靠颜色。

## 6. 针对已有项目的技术实施要求

### 6.1 首先识别项目技术栈

- 如果是 **Flutter**：优先检查 `ThemeData`、`ColorScheme`、`ThemeExtension`、公共颜色常量、`MaterialApp` 主题以及现有 Cupertino/Material 组件；保留路由与状态管理逻辑。
- 如果是 **React / Next.js**：优先检查 CSS Variables、Tailwind 配置/主题变量、全局样式、已有组件库（如 Ant Design、shadcn/ui）主题配置。
- 如果是 **Vue / Nuxt**：优先检查 CSS Variables、UnoCSS / Tailwind 配置、全局样式、组件库主题覆盖与页面级 scoped styles。
- 如果是其他技术栈：沿用原有约定建立等价的主题变量。

### 6.2 优先进行的修改

1. 找到并统一应用颜色 Token。
2. 统一按钮、卡片、输入框、导航、文字的通用样式。
3. 逐页处理首页、明细、记账、统计与设置（以实际存在页面为准）。
4. 清理明显冲突的历史硬编码配色，但避免无差别全仓搜索替换。
5. 检查选中态、禁用态、错误态、深色模式（若已有）、响应式与安全区域。

### 6.3 兼容性约束

- 尊重系统字体缩放、屏幕尺寸与安全区域（包括刘海屏、底部 Home Indicator）。
- 保持原有 iOS / Android 平台差异处理。
- 如果已有深色主题，**不可直接删除**；本规范的色值针对浅色主题，深色主题应保留原有功能并采用对应深色 Token。若范围不允许改深色主题，至少确保切换后不出现文字不可见等问题。
- 不增加不必要的依赖；若确需增加，说明必要性和影响。
- 保留现有多语言资源与日期、货币的本地化格式。
- 任何修改不得影响存储数据和历史账单。

## 8. 验收标准

改造完成后，应符合以下标准：

1. **整体风格统一**：全局以蓝白浅色为主，没有明显与主题冲突的旧品牌色。
2. **看起来简约**：没有大面积花哨渐变、强阴影、3D 图表、过多彩色卡片。
3. **功能不退化**：账单增删改查、分类、统计、预算、原有页面导航等功能仍与改造前一致。
4. **金额可读**：收入/支出/结余清晰区分，显示格式与计算值均未发生错误变化。
